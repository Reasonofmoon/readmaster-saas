# ReadMaster Lesson Studio 프로젝트 하네스 스펙

## 문서 상태

- 목적: 승인된 설계를 구현·운영 가능한 프로젝트 하네스의 기준으로 고정한다.
- 범위: 역할, 단계, 데이터 계약, 사람 승인, 검증, 실패 복구, 진화 규칙을 정의한다.
- 성격: 구현 중립적인 설계·운영 스펙이다. 이 문서 자체는 애플리케이션 코드, 런타임 설정, 외부 서비스 설정을 정의하지 않는다.
- 기준일: 2026-08-24

## 1. 목표

ReadMaster Lesson Studio는 단순한 AI 문제 생성기가 아니라, 강사가 가진 영어 교재를 실제 수업에 사용할 수 있는 자료 패키지로 변환하는 강사용 제작 시스템이다.

한 번의 작업은 원문 교재를 보존하면서 다음 산출물을 만들 수 있어야 한다.

- 학생용 워크북
- 강사용 수업안
- 테스트 A/B형 자료
- 정답·해설
- 단어 자료
- 문항 유형·난도·CEFR·영역 분석 리포트
- 학생용·교사용·정답해설 출력 파일의 패키지

모든 생성 항목은 원문 근거를 추적할 수 있어야 하며, 구조 검수와 콘텐츠 검수를 통과한 승인 버전만 출력 단계로 이동한다. 강사가 최종 결정권을 가지며, 사람의 응답이 필요한 상태를 자동 승인하거나 자동 발행하지 않는다.

## 2. 범위

### 포함

- PDF, DOCX, HWP, HWPX, 이미지 등 교재 입력의 검증과 구조화
- 페이지·섹션·블록·문항·에셋·파싱 경고를 포함하는 Canonical Document 표현
- 생성 결과별 원문 `sourceRefs` 보존
- 어휘, 문항, 해설, 수업안, 테스트 변형 자료의 병렬 생성
- 근거·교육 품질 자동 QA와 문항 단위 재시도
- `structureReview`, `contentReview` 강사 승인 게이트
- 학생용·교사용·정답해설 산출물 분리
- 원자료·초안·검수본·발행본의 불변 버전 관리
- 출력 체크섬, 입력 버전, 템플릿 버전, 렌더러 버전 기록
- 상태, 경고, 재시도 범위, 승인, 실패, 변경 이력 기록
- 공개·비공개 데이터 경계와 민감한 내용의 로그 비노출

### 제외

- 이 문서에서의 웹·API·DB·큐·파서·LLM·렌더러 구현
- 특정 언어, 프레임워크, 모델 공급자, 저장소 제품의 확정
- `AGENTS.md`, 역할 카드, `docs/harness/` 파일, 스크립트, `package.json`의 생성
- 운영 인프라 구축, 배포, 결제, 외부 고객용 SaaS 기능, 마켓플레이스
- 실시간 공동 편집, 자동 발행, 사람 승인 우회
- 원본 교재나 OCR 본문, 정답 데이터, 내부 프롬프트, 비밀값의 저장·공개

## 3. 현재 감사

승인 설계의 초기 감사 기준으로 이 작업 폴더는 구현물이 없는 신규 작업 폴더였다. 애플리케이션 소스, `package.json`, 프로젝트 하네스의 권위 있는 파일이 없었으며 Git 저장소도 아니었다. 확인 명령 `git status --short`는 `fatal: not a git repository`를 반환했다.

따라서 이 스펙은 기존 구현과의 호환성을 전제로 하지 않으며, 실제 실행 명령은 `package.json`이 생성되고 해당 파일에 명시된 뒤 존재 여부를 확인하여 등록한다. 아직 존재하지 않는 명령, 의존성, 서비스, 경로를 실행 계약으로 간주하지 않는다.

## 4. 아키텍처 원칙

### 기본 패턴

주 아키텍처는 체크포인트를 갖는 순차 파이프라인이며, 승인된 구조 이후에는 독립적인 생성 작업을 제한적으로 병렬 실행하고, 독립 QA가 결과를 합치는 Generate–Verify 흐름을 사용한다.

```text
업로드·파싱
  → 구조 QA
  → [강사 structureReview]
  → 어휘·문항·해설·수업안 병렬 생성
  → 근거·콘텐츠 QA
  → [강사 contentReview]
  → 학생용·교사용·정답해설 렌더링
  → 출력 QA
  → 버전 패키징
```

### 불변식

1. `sourceRefs`가 없는 생성 항목은 다음 단계로 전달하지 않는다.
2. 구조 승인과 콘텐츠 승인을 모두 받은 버전만 조판·패키징한다.
3. 승인 버전은 덮어쓰지 않으며, 변경은 새 버전과 새 상태를 만든다.
4. 실패는 가능한 가장 작은 단위로 격리하고 재시도한다.
5. 출력과 파일 저장처럼 부작용이 있는 작업은 동일 입력에서 중복 실행되어도 결과가 중복되지 않도록 idempotency key를 사용한다.
6. 사람 승인이 필요한 상태에서는 자동 승인·자동 발행을 수행하지 않는다.

### 상태 원칙

작업은 최소한 `pending`, `running`, `waitingForHuman`, `approved`, `rejected`, `stale`, `failed`, `completed` 상태를 구분한다. 파서 수정으로 영향받은 섹션과 그 파생 산출물은 `stale`로 표시하고, 승인된 이전 버전은 보존한다.

## 5. 역할과 책임

하네스 역할은 다음 다섯 개로 제한한다. 각 역할은 자신의 산출물을 생성하고 공통 handoff packet으로 다음 역할에 넘긴다.

### 5.1 `orchestrator`

- 임무: 작업 상태, 단계 순서, 체크포인트, 승인 대기, 재시도, 통합을 조정한다.
- 입력: 작업 요청, 프로젝트 설정, 현재 버전, 이전 단계의 handoff packet.
- 출력: 다음 단계의 작업 지시, 상태 전이, 승인 요청, 최종 통합 packet.
- 사용할 수 있는 능력: 하네스 계약 조회, 실행 기록 조회, 단계별 검증.
- 하지 않는 일: 문항·해설을 직접 생성하지 않으며, 강사 승인을 대신하지 않는다.
- 실패·상향: 계약 위반은 해당 단계에 반환하고, 반복 실패·사람 결정 필요·범위 변경은 `waitingForHuman` 또는 상위 운영자 검토로 올린다.

### 5.2 `document-parser`

- 임무: 입력 문서를 Canonical Document로 변환하면서 원문 순서와 근거 위치를 보존한다.
- 입력: 검증된 원본 파일, 문서 메타데이터, 파서 설정.
- 출력: Canonical Document, 에셋 연결, 파싱 경고, 문서 해시.
- 사용할 수 있는 능력: 형식별 파싱, 레이아웃·표·이미지·수식 관계 추출, OCR 보조.
- 하지 않는 일: 문항의 교육적 정답을 창작하거나 구조가 승인되기 전에 생성 자료를 만들지 않는다.
- 실패·상향: 형식 판별·구조·근거 위치가 불확실하면 경고와 실패 범위를 남기고 재시도·섹션 축소·사람 구조 검수로 올린다.

### 5.3 `lesson-builder`

- 임무: 구조 승인된 원문에서 요청된 수업 자료를 생성한다.
- 입력: 승인된 Canonical Document, 생성 프리셋, 학년·학생 수준·목표 CEFR·출력 자료 설정.
- 출력: 어휘, 문항, 해설, 수업안, 테스트 변형과 각 항목의 `sourceRefs`.
- 사용할 수 있는 능력: 자료 유형별 생성, 난도 조정, 문항 단위 재생성, 출력 대상별 정보 분리.
- 하지 않는 일: 근거 없는 항목을 통과시키거나 QA·강사 승인을 스스로 판정하지 않는다.
- 실패·상향: 스키마 오류는 오류 필드부터 재생성하고, 반복 실패는 더 작은 섹션·호환 폴백·문항 격리·강사 검수로 전환한다.

### 5.4 `evidence-content-qa`

- 임무: 구조·정답 근거·교육 품질·공개 대상 분리를 독립적으로 검증한다.
- 입력: Canonical Document, lesson-builder 산출물, 생성 설정, 이전 QA 결과.
- 출력: 항목별 통과·실패 판정, 근거 위치, 실패 사유, 재시도 범위, 전체 QA 요약.
- 사용할 수 있는 능력: 정답 근거 대조, 중복·복수 정답·오답 품질·CEFR 점검, 학생용 정답 노출 점검.
- 하지 않는 일: 실패한 항목을 묵인하거나 강사 승인·출력 승인을 대신하지 않는다.
- 실패·상향: 실패 항목만 builder로 되돌리고, 해결되지 않거나 근거가 불명확한 항목은 격리하여 강사 결정으로 올린다.

### 5.5 `renderer-export`

- 임무: 콘텐츠를 변경하지 않고 승인된 버전을 학생용·교사용·정답해설 출력물로 조판·패키징하고 출력 품질을 검증한다.
- 입력: 두 승인 게이트를 통과한 버전, 출력 설정, 템플릿·렌더러 버전.
- 출력: 분리된 출력 파일, export manifest, 체크섬, 출력 QA 결과.
- 사용할 수 있는 능력: PDF·DOCX 등 승인된 출력 포맷 생성, 인쇄 레이아웃 검증, 패키지 구성.
- 하지 않는 일: 승인되지 않은 콘텐츠를 출력하거나 조판 중 원문·정답·해설을 임의 변경하지 않는다.
- 실패·상향: 의미 불일치·레이아웃 오류는 출력 범위만 재렌더링하고, 원인 콘텐츠 오류는 QA 또는 강사 검수로 되돌린다.

## 6. 파일 레이아웃

다음은 프로젝트 하네스의 목표 레이아웃이다. 이 스펙 작성 작업에서는 아래 파일을 생성하지 않는다.

```text
AGENTS.md
docs/harness/
├── manifest.md
├── agents/
│   ├── orchestrator.md
│   ├── document-parser.md
│   ├── lesson-builder.md
│   ├── evidence-content-qa.md
│   └── renderer-export.md
├── contracts/
│   ├── handoff-packet.md
│   ├── canonical-document.md
│   ├── review-gates.md
│   └── export-manifest.md
└── runs/
    └── README.md

tasks/
├── SPEC-readmaster-lesson-studio-harness.md
└── lessons.md
```

`AGENTS.md`는 전체 계약을 중복 기록하지 않고 `docs/harness/manifest.md`를 진입점으로 가리킨다. 실행 기록에는 작업별 날짜·작업명 디렉터리를 사용하며, 민감한 본문은 기록하지 않는다.

## 7. 공통 계약

### 7.1 Handoff packet

모든 역할 사이의 전달 단위는 다음 필드를 갖는다.

```text
jobId
projectId
sourceHash
documentVersion
schemaVersion
artifactPath
status
warnings[]
requiredHumanGate
retryScope
createdAt
```

필드는 누락되지 않아야 하며, `artifactPath`는 내부 산출물 위치를 가리키고 원문 본문을 대신하지 않는다. `sourceHash`와 `documentVersion`은 입력과 산출물의 연결을 확인하는 데 사용한다.

### 7.2 Canonical Document

정규 문서는 다음 구조를 갖는다.

```text
Document
├── metadata
├── pages[]
├── sections[]
├── blocks[]
├── questions[]
├── assets[]
└── parseWarnings[]
```

문항은 최소한 `questionId`, `questionNumber`, `questionType`, `stem`, `passageRefs[]`, `options[]`, `correctAnswer`, `explanation`, `difficulty`, `cefrLevel`, `skillTags[]`, `sourceRefs[]`, `confidence`, `reviewStatus`를 가진다.

`sourceRefs[]`의 각 항목은 `documentId`, `pageNumber`, `blockId`, `startOffset`, `endOffset`, `sourceQuote`를 보유한다. 생성 항목의 정답과 해설은 원문 페이지와 블록까지 역추적할 수 있어야 한다.

### 7.3 Review gates

두 승인 게이트는 `gateName`, `targetVersion`, `reviewer`, `decision`, `reviewedAt`, `reason`을 기록한다.

- `structureReview`: 파싱된 섹션·블록·문항 연결, 보기 순서, 정답 표시, 표·이미지·수식 누락을 검토한다. 승인 전 lesson-builder를 실행하지 않는다.
- `contentReview`: 생성 자료, 정답 근거, 오답, 난도·CEFR, 학생용 공개 범위를 검토한다. 승인 전 renderer-export를 실행하지 않는다.

결정은 승인·수정 요청·반려로 구분하며, 승인되지 않은 버전은 다음 단계로 진행하지 않는다. 응답이 없으면 `waitingForHuman`에 머문다.

### 7.4 Export manifest

출력 매니페스트는 학생용·교사용·정답해설 파일을 서로 구분하고, 입력 버전, 템플릿 버전, 렌더러 버전, 파일 목록, 각 파일 체크섬, 생성 시각, QA 결과를 기록한다. 기존 출력은 덮어쓰지 않고 새 버전으로 만든다.

## 8. 스킬 지도

### 재사용

- `harness`: 역할·계약·실행·검증·진화 설계
- `brainstorming` → `writing-plans`: 기능 의도와 다단계 변경 계획
- `ocr`: 스캔 문서와 이미지 자료의 텍스트 추출
- `edu-content`: 영어 교육 문항과 설명 품질 기준
- `system-reference`: 상태·큐·스토리지·멀티테넌트 경계 설계 참고
- `test-driven-development`: 기능·버그 수정 시 검증 우선 구현
- `systematic-debugging`: 실패·예상 밖 동작의 원인 분석
- `code-review`: 계약·보안·회귀 검토
- `verification-before-completion`: 완료 주장 전 검증
- `supabase-patterns`: 실제 Supabase 멀티테넌트·RLS를 도입할 때 조건부 사용
- `workbook`, `nonfiction`: 인쇄형 출력 품질 패턴이 필요할 때 조건부 참고

### 신규 생성 후보와 제외

반복 작업과 실패 패턴이 확인되기 전에는 새 글로벌 스킬을 만들지 않는다. 재사용성이 입증된 뒤 프로젝트 로컬 후보로 `readmaster-canonical-document`, `readmaster-package-gates`를 검토한다. 블로그 게시, TTS, 번역, NotebookLM, Google ADK, Adobe 템플릿 관련 스킬은 Lesson Studio 핵심 하네스의 트리거에서 제외한다.

## 9. 실행 흐름

| 단계 | 입력 | 담당 | 출력·통과 조건 |
| --- | --- | --- | --- |
| 1. 업로드 검증 | 원본 파일, 프로젝트 설정 | orchestrator / document-parser | 파일 형식·크기·무결성 검증, `sourceHash` |
| 2. 파싱·정규화 | 검증된 파일 | document-parser | Canonical Document, 에셋, 경고 |
| 3. 구조 QA | Canonical Document | evidence-content-qa | 구조 오류 목록과 수정 범위 |
| 4. 구조 승인 | 구조 QA 결과 | 강사 | `structureReview` 승인 또는 수정 요청 |
| 5. 자료 생성 | 구조 승인 버전, 프리셋 | lesson-builder | 자료별 초안과 항목별 `sourceRefs` |
| 6. 콘텐츠 QA | 생성 초안, 원문 | evidence-content-qa | 근거·교육 품질 판정, 재시도 범위 |
| 7. 콘텐츠 승인 | QA 통과 자료 | 강사 | `contentReview` 승인 또는 수정 요청 |
| 8. 렌더링·패키징 | 승인 버전, 출력 설정 | renderer-export | 분리 출력물, export manifest |
| 9. 출력 QA | 출력물, 승인 버전 | renderer-export / orchestrator | 의미 일치·인쇄 품질·체크섬 확인, 완료 버전 |

orchestrator는 각 단계의 체크포인트와 handoff packet을 저장하고, 실패한 단계 또는 항목부터 재개한다. 콘텐츠 생성은 어휘·문항·해설·수업안처럼 서로 독립적인 단위로 병렬화할 수 있으나, 통합 전 각 결과의 계약과 근거를 확인한다.

## 10. 공개·비공개 경계

### 비공개

원본 교재, OCR·파싱 텍스트, Canonical Document, 정답·해설 초안, 강사 메모, 내부 프롬프트, 모델 비용·실행 세부정보는 기본 비공개다. 실행 기록에는 본문 대신 해시, 버전, 상태, 경고, 내부 산출물 식별자만 남긴다.

### 공유 가능

강사가 승인하고 적절한 권한을 부여한 학생용·교사용·정답해설 출력물만 공유 대상이 될 수 있다. 승인 전 초안과 근거 원문은 공유 경계를 넘지 않는다.

비밀값, API 키, 인증 정보, 원문 내용, 학생 개인정보는 이 하네스 문서와 공개 로그에 기록하지 않는다.

## 11. 검증 기준

### 구조 검증

- 목표 레이아웃의 역할·계약·실행·기록 파일이 서로 연결된다.
- 모든 역할의 입력·출력·금지사항·실패 경로가 정의된다.
- 모든 단계에 입력, 담당, 출력·통과 조건이 있다.
- handoff packet, Canonical Document, review gate, export manifest의 필드가 일관된다.

### 트리거 검증

Lesson Studio 개발, 교재 파싱, 원문 근거형 문항 생성·검수, 학생용·교사용 출력 패키지 요청에는 이 하네스를 적용한다. 단순 블로그 게시, TTS, 번역, NotebookLM 산출물 요청에는 적용하지 않는다.

### 실행·명령 검증

실제 명령은 `package.json`이 존재한 뒤 해당 파일에 정의된 내용을 확인하고서만 하네스 매니페스트에 등록한다. 존재하지 않는 빌드·테스트·린트·배포 명령을 미리 사용하거나 기록하지 않는다. 코드가 변경되는 모든 작업은 변경 후 `npx tsc --noEmit`을 반드시 실행하며, 관련 범위의 검증 결과와 실패 원인을 실행 기록에 남긴다.

### 제품 품질 검증

- 모든 생성 항목에 유효한 `sourceRefs`가 있다.
- 정답은 원문에서 도출되고 해설은 근거 위치를 제시한다.
- 문항 중복·복수 정답·부적절한 오답·지정 수준 불일치를 탐지한다.
- 학생용 출력에 정답·해설이 노출되지 않는다.
- 승인된 동일 버전의 학생용·교사용·정답해설 간 의미가 일치한다.
- 실제 출력의 페이지·여백·답안 공간·페이지 번호 등 인쇄 조건을 확인한다.

## 12. 실패 처리와 재시도

실패는 전체 파이프라인보다 좁은 범위에서 복구한다.

```text
스키마 오류
  → 오류 필드 재생성
  → 원문 Section 축소
  → 동일 계약을 지원하는 폴백 경로
  → 문제 항목 격리
  → 강사 검수 대기
```

- 구조 오류: 영향을 받은 섹션·문항만 `stale` 처리하고 파서 또는 구조 검수로 되돌린다.
- 생성 오류: 오류 필드나 문항만 재생성하며, 통과한 항목을 불필요하게 재생성하지 않는다.
- QA 오류: 실패 항목의 사유·근거·`retryScope`를 기록하고 builder로 되돌린다.
- 승인 반려: 강사 사유를 보존한 새 초안 작업을 만들고 승인 버전은 변경하지 않는다.
- 렌더링 오류: 출력물 범위만 idempotency key로 재렌더링하며, 콘텐츠 변경이 필요하면 QA·승인 흐름으로 되돌린다.
- 반복 실패 또는 판단 불가: 자동 발행하지 않고 `waitingForHuman` 또는 `failed`로 격리한다.

## 13. 진화 규칙

- 사용자의 교정은 민감한 본문 없이 `tasks/lessons.md`에 일반화된 실패 패턴, 영향 계약, 재발 방지책으로 기록한다.
- 같은 실패가 반복되면 관련 역할 카드, 데이터 계약, 검증 항목을 함께 갱신한다.
- 변경 이력에는 날짜, 대상, 변경 이유, 검증 결과를 남긴다.
- 반복 사용과 효과가 확인된 절차만 프로젝트 로컬 스킬 후보로 승격한다.
- 역할이나 스킬이 중복되면 새 역할을 추가하지 않고 책임을 병합하거나 기존 역할의 계약을 확장한다.
- 계약 변경은 영향받는 생산자·소비자와 버전을 함께 갱신하고, 이전 승인 버전의 해석 가능성을 보존한다.

## 14. 수용 기준

이 스펙은 다음을 모두 만족할 때 수용된다.

1. 제품 목표가 문제 생성이 아닌 원문 근거형 수업 패키지 제작으로 명확히 정의되어 있다.
2. 포함 범위와 제외 범위가 구현·운영·배포 경계를 구분한다.
3. 신규 비-Git 작업 폴더라는 초기 감사와 명령 검증 조건이 기록되어 있다.
4. 체크포인트 파이프라인, 제한적 병렬 생성, 독립 QA, 버전 불변 원칙이 일관되게 연결되어 있다.
5. 다섯 역할 각각에 임무, 입출력, 허용 능력, 금지사항, 실패·상향 경로가 있다.
6. 목표 파일 레이아웃과 공통 handoff·문서·승인·출력 계약이 정의되어 있다.
7. `sourceRefs` 필수 조건과 승인 전 조판 금지 조건이 명시되어 있다.
8. 사람 승인 게이트, 개인정보·원문 비공개 경계, 자동 승인 금지가 명시되어 있다.
9. 재시도 범위, 격리, `stale` 처리, idempotency 원칙이 정의되어 있다.
10. 스킬 재사용·제외·승격 규칙과 구조·트리거·명령·제품 품질 검증이 포함되어 있다.
11. `package.json` 이후 명령 확인과 코드 변경 후 `npx tsc --noEmit` 필수 조건이 포함되어 있다.
12. 이 파일 외의 애플리케이션 코드, 의존성, 저장소, 비밀값, 원본 교재 내용이 포함되어 있지 않다.
